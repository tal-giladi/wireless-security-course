# 03.2 · Recorded-data setup — tools, supplied captures, and checksums

The recorded-data path needs no radio, but it does need a small, correct toolchain and a habit you will keep for the rest of your career: never trust a capture you have not checksummed. This lesson installs the analysis tools the course uses, walks you through fetching the supplied captures from the module zip, and verifies each file against the SHA-256 recorded in [`../../labs/common/CAPTURES.md`](../../labs/common/CAPTURES.md) — and it is honest that those captures are generated by a script and are marked PENDING until a real run has produced and checksummed them.

> [!NOTE]
> Tool versions move. This lesson names the technique and the tool; a newer version with a changed flag
> is a troubleshooting exercise, not a wall. Record the versions you actually install in your own notes
> (see [`../../TOOLS.md`](../../TOOLS.md)), because those are what your results depend on.

## Why this matters

Every later analysis module — recon, capture dissection, WPA2/WPA3 cracking — runs on these four tools and on files you did not create yourself. If a file is corrupted in transit, truncated, or quietly the wrong file, you can burn an afternoon "debugging" an attack that was never going to work, or worse, report a result that is an artifact of a bad capture. A checksum turns "I think this is the right file" into "this is byte-for-byte the file the author verified." Provenance — who made it, how, with what credentials, under what licence — is the difference between a capture you may analyse and redistribute and one you had no right to touch. These habits are cheap now and non-negotiable later.

## Learning objectives

- Install and confirm **Wireshark/tshark, hashcat, hcxtools, and the aircrack-ng suite**.
- Fetch the supplied captures and **verify each against its SHA-256** before analysing it.
- Explain **why provenance and checksums matter** for every capture you analyse or ship.

## Concept

### The recorded-data toolchain

Four tools cover the whole recorded path. Each has a distinct job:

- **Wireshark / `tshark`** — open a `.pcap`/`.pcapng`, dissect 802.11 frames, and filter (the GUI for exploring, `tshark` for scripting). This is how you *read* a capture.
- **aircrack-ng suite** — here used for analysis and cracking of captures (`aircrack-ng` itself); the capture/injection tools in the suite belong to the physical path.
- **hcxtools** — chiefly `hcxpcapngtool`, which converts a `.pcapng` containing a handshake or PMKID into the `hc22000` hashline format hashcat consumes.
- **hashcat** — the cracker. **Mode `-m 22000`** (WPA-PBKDF2-PMKID+EAPOL) is the modern mode that handles both captured 4-way handshakes and PMKIDs in one format.

The pipeline for the cracking exercises is therefore: **capture (supplied) → `hcxpcapngtool` → `.hc22000` → `hashcat -m 22000` → result.** You read the same capture in Wireshark to understand *why* it does or does not crack.

### Installing on the lab OS

On a Debian/Kali/Ubuntu lab VM the packages are standard. Versions are `VERIFY` until you confirm them on your own build — record what you get.

```bash
sudo apt update
sudo apt install -y wireshark tshark hashcat hcxtools aircrack-ng
# confirm each is present and note the version:
tshark --version | head -1
hashcat --version
hcxpcapngtool --version
aircrack-ng --help | head -2
```

`hcxpcapngtool` ships inside the `hcxtools` package (distinct from `hcxdumptool`, which is a *capture* tool for the physical path — you do not need it here). If your distro lacks a recent `hcxtools`, build it from source ([the upstream repo](https://github.com/ZerBea/hcxtools)) and record the commit.

### Getting the supplied captures

The captures the recorded path analyses live in the module zips, generated by [`../../labs/common/gen-captures.sh`](../../labs/common/) on the virtual path with synthetic credentials — never from any real network. The set and what each file should produce is listed in [`../../labs/common/CAPTURES.md`](../../labs/common/CAPTURES.md): a clean handshake that cracks with the bounded wordlist, a **partial** handshake that does not, a PMKID example, and a **strong-password** handshake that correctly does *not* crack.

> [!IMPORTANT]
> The capture binaries are **PENDING** until someone runs `gen-captures.sh` and records the real
> checksums. Until then, [`../../labs/common/CAPTURES.md`](../../labs/common/CAPTURES.md) shows every
> row as `PENDING` with a `—` checksum, and this lab cannot be completed against real files yet. That is
> deliberate honesty: a checksum is only worth anything if it comes from a real run, never hand-written.
> This is tracked in [`../../TODO_FOR_TAL.md`](../../TODO_FOR_TAL.md).

### Why checksums and provenance are not optional

A **SHA-256** is a 64-hex-character fingerprint of the file's exact bytes. If one byte changes, the fingerprint changes completely, so comparing the hash you compute against the one the author recorded proves you have the identical file — not a truncated download, not a look-alike. **Provenance** answers the other half: this capture was generated in our own lab, on simulated radios, with synthetic credentials (`Lab-WiFi-Passw0rd!`), licensed CC0 for redistribution. Together they let you say, defensibly, "this is the verified file, it was made legitimately, and here is the result it is supposed to produce." That sentence is the foundation of every evidence package you will ever hand a client.

## Hands-on

Path **R** only. You install the toolchain and verify the supplied captures against their recorded hashes. Nothing here transmits.

### Guided walkthrough — install, fetch, verify

1. Install the four tools (commands above) and record each version in your notes.
2. Download the module zip for a capture-using module (e.g. Module 1 or Module 6) and extract its `captures/` folder.
3. Open [`../../labs/common/CAPTURES.md`](../../labs/common/CAPTURES.md) and read the provenance table: for each file, note **how it was generated**, **what it should produce**, and its **recorded SHA-256** (or `PENDING`).
4. Compute the hash of each file and compare:

   ```bash
   sha256sum captures/*.pcapng captures/*.hc22000
   # or verify a whole manifest at once:
   sha256sum -c captures/CHECKSUMS.txt
   ```

5. For a file whose row is **verified**, confirm your hash matches character-for-character. For a **PENDING** row, note that you cannot verify yet and record that in your lab notebook — do not pretend a missing checksum passed.
6. Open one capture in Wireshark and confirm it parses and shows 802.11 frames — a sanity check that the file is what the table claims.

### Lab — verify the supplied capture set

> [!NOTE]
> **Lab paths:** R (install tools, fetch and checksum supplied captures — no hardware, nothing transmitted; proves you can set up the analysis toolchain and verify a capture's integrity and provenance, not that you captured anything).
> **Start state:** a Linux lab VM with Internet for package install; the relevant module zip extracted.
> **Duration:** ~35 min.
> **Artifacts:** a notes entry listing installed tool versions; the `sha256sum` output for each supplied capture with PASS/`PENDING` noted against [`../../labs/common/CAPTURES.md`](../../labs/common/CAPTURES.md); one capture confirmed to open in Wireshark.
> **Troubleshooting:** `hcxpcapngtool: command not found` → install `hcxtools` (not `hcxdumptool`), or build from source and record the commit. A hash mismatch → re-extract the zip; a truncated download is the usual cause. A row still `PENDING` → the capture set has not been generated yet; verify what you can and mark the rest unverified. Wireshark shows nothing → confirm you opened a `.pcapng`, not the `.hc22000` text file.
> **Cleanup:** none; the tools stay installed for the rest of the course.

## Exercise

A teammate sends you a `handshake.pcapng` by chat and says "crack this, the password's in the lab list." You have no checksum and no note of where the file came from. List what you should establish *before* you spend cracking time on it, and explain what could go wrong if you skip those checks.

<details>
<summary>Hint</summary>

Two separate questions: is the file *intact and the one they meant* (integrity), and *were they entitled to capture and share it* (provenance/licence)? What does a SHA-256 give you, and what does it not — and what does a chat transfer not tell you about where the traffic came from?
</details>

<details>
<summary>Reference answer</summary>

Before cracking, establish **integrity** and **provenance**. Integrity: get the author's recorded SHA-256 and confirm the file you received matches it, so you are not debugging a truncated or wrong file — a chat transfer can silently corrupt or swap it. Provenance: confirm the capture came from **owned equipment with synthetic credentials** (the only legitimate source in this course), not a real network someone had no right to intercept; without that, analysing it could be unlawful and is certainly not reportable. Skipping these risks (a) wasting hours on a corrupt or partial capture that was never going to crack, and (b) handling intercepted real traffic. A checksum proves the bytes are identical; it does **not** prove the capture was made legally — provenance is the separate, equally necessary check. The correct move is to ask for the checksum and the provenance note before running hashcat.
</details>
