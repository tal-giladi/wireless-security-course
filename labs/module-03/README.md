# Module 3 labs — Building your lab (three paths)

Module 3 is where you build the lab itself, so its "labs" are setup and verification, not attacks.
Nothing in this module needs to attack anything, and only lessons 03.4/03.5 touch real radio — and even
those are optional, because the whole course is completable on the recorded (R) and virtual (V) paths
with zero purchases.

## In this module's zip

- This README.
- From [`../common/`](../common/): `hwsim-up.sh`, `hwsim-down.sh` (bring the `mac80211_hwsim` radios
  up/down), `setup-check.sh` (verify the toolchain and list versions), `reset-lab.sh` (return any
  interface to managed mode and stop services), and the capture/wordlist generators
  (`gen-captures.sh`, `make-wordlists.sh`) used by the modules that ship captures.
- No new capture files are introduced by Module 3. The supplied captures the recorded path verifies in
  lesson 03.2 live in the other modules' zips and are catalogued in [`../common/CAPTURES.md`](../common/CAPTURES.md).

## Paths supported in this module

| Lesson | Path(s) | What the lab proves | What it does NOT prove |
|---|---|---|---|
| 03.1 choosing your path | R | choosing a path and stating its limits honestly | any capture, injection, or RF |
| 03.2 recorded-data setup | R | installing the analysis toolchain; verifying a capture's integrity + provenance | live capture, injection, RF |
| 03.3 virtual labs (`mac80211_hwsim`) | V | configuring an AP + client and reproducing the join/handshake flow | real RF, drivers, range, interference, injection |
| 03.4 the physical rig | P | real monitor mode + injection on owned hardware; regulatory/driver reality | — (this is the RF ground truth) |
| 03.5 Windows VMs + USB passthrough | P (fallback V) | plumbing a real adapter into a Linux VM so monitor/injection become possible | the RF capabilities themselves (verified in 03.4) |

**R and V never grant physical-capture or injection credit** ([`../../curriculum/assessment-rubrics.md`](../../curriculum/assessment-rubrics.md)).

## Setup toolchain (lesson 03.2)

Install and confirm the recorded-data analysis tools, then verify any supplied capture before trusting
it. Versions are `VERIFY` until you confirm them on your own build — record what you install
([`../../TOOLS.md`](../../TOOLS.md)).

```bash
sudo apt install -y wireshark tshark hashcat hcxtools aircrack-ng
./labs/common/setup-check.sh            # reports presence + versions; read-only, transmits nothing
sha256sum -c captures/CHECKSUMS.txt     # verify a supplied capture set against recorded hashes
```

> [!IMPORTANT]
> The supplied captures are generated by [`../common/gen-captures.sh`](../common/) on the virtual path
> and are **PENDING** until a real run records their checksums ([`../common/CAPTURES.md`](../common/CAPTURES.md)).
> Verify what has a recorded checksum; mark anything still `PENDING` as unverified. Never hand-write a checksum.

## Virtual (V) setup lab — lesson 03.3

Reproduce a real join with no hardware and no transmission:

```bash
sudo ./labs/common/hwsim-up.sh 2        # load mac80211_hwsim -> wlan0, wlan1
# AP on wlan0 (WPA2, SSID LAB-JOIN, synthetic passphrase) via hostapd  (see lesson 03.3)
# client on wlan1 via wpa_supplicant; watch auth -> assoc -> 4-way handshake
iw dev wlan1 link                       # expect "Connected to <BSSID>"
sudo ./labs/common/hwsim-down.sh        # cleanup: remove simulated radios
```

- **Start state:** Linux VM; `mac80211_hwsim`, `hostapd`, `wpa_supplicant`, `iw` installed.
- **Expected artifacts:** `hostapd`/`wpa_supplicant` logs showing authentication, association, and the
  EAPOL handshake; the `iw dev wlan1 link` line naming the simulated BSSID.
- **Success criteria:** the client reaches the connected state and you can point to each step in order.
- **Troubleshooting:** module not loaded (`modprobe mac80211_hwsim radios=2`); interface busy
  (`sudo airmon-ng check kill` or `reset-lab.sh`); SSID/PSK/channel mismatch (make them match).
- **Cleanup:** stop the daemons, run `hwsim-down.sh`. Nothing transmitted — no RF cleanup.

## Physical (P) setup lab — lessons 03.4 and 03.5

> [!WARNING]
> Monitor mode and injection transmit **real radio in range**. Owned equipment only, on your allowlist,
> at minimum TX power, on a chosen channel, with stop conditions and cleanup
> ([`../../lessons/module-00/lesson-03.md`](../../lessons/module-00/lesson-03.md)). A private subnet does
> not contain radio. Prefer the virtual path for anything that does not strictly need real RF.

```bash
lsusb ; sudo dmesg | tail -40           # identify chipset + the driver that claimed it
iw reg get ; sudo iw reg set <COUNTRY>  # set your legal regulatory domain
sudo airmon-ng check kill
sudo ip link set wlan1 down
sudo iw dev wlan1 set type monitor
sudo ip link set wlan1 up
iw dev wlan1 info                       # confirm "type monitor"
sudo aireplay-ng -9 wlan1               # injection test: look for "Injection is working!"
sudo ./labs/common/reset-lab.sh         # restore managed mode + services when done
```

- **Buy by chipset, verify the revision:** known-good chipsets are AR9271 (2.4-only), MT7612U and
  MT7921U (dual-band, mainline), RTL8812AU (dual-band, out-of-tree DKMS — pin a kernel). Confirm the
  exact model **and hardware revision** before buying — the TL-WN722N v1 (AR9271) vs v2/v3 (RTL8188EUS)
  trap is the canonical example. See [`../../curriculum/lab-matrix.md`](../../curriculum/lab-matrix.md).
- **Monitor, injection, and AP mode are separate capabilities** — verify each; mark untested cells `VERIFY`.
- **Windows-hosted VM (lesson 03.5):** USB passthrough needs the VirtualBox Extension Pack (match the
  version) or VMware; Hyper-V has no general USB passthrough for a Wi-Fi adapter. Match the USB 2.0/3.0
  controller to the adapter. When passthrough fights you and the goal is protocol rather than RF, fall
  back to the virtual path — it needs no passthrough.
- **Expected artifacts:** `iw dev wlan1 info` showing `type monitor`; the `aireplay-ng -9` result; a
  lab-matrix notes row recording monitor/injection as verified or `VERIFY` with model + revision +
  driver + kernel.
- **Cleanup:** `reset-lab.sh` returns the interface to managed mode and restores services; reset the
  regulatory domain if you changed it (`sudo iw reg set <COUNTRY>`).

## Cleanup (whole module)

Recorded-data setup transmits nothing. The virtual lab is reset by `hwsim-down.sh`; the physical lab by
`reset-lab.sh` (plus a regulatory-domain reset if you changed it). `reset-lab.sh` is the catch-all for
any state left behind.
